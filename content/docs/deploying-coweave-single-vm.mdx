# Self-Hosting CoWeave Enterprise: From Tarball to Running Platform

You just received the CoWeave Enterprise package. This is the complete walkthrough for getting from a fresh VM to a running platform — the workflow engine, the AI service, **and** Context Engineering Studio — explained step by step with the reasoning behind each move.

**Time budget — be honest with yourself**: plan a **half-day** of focused work for your *first* deploy. The commands themselves run in well under an hour; what eats the time the first time is provisioning (VM + data disk), decisions (DNS, SMTP, storage sizes), and understanding what each step does. Once you've done it once, a repeat deploy is **30–45 minutes**.

This guide is structured so you can read it once end-to-end before you start typing, then follow it step by step with confidence.

---

## What Enterprise actually is

CoWeave Enterprise is deployed as one platform across several Kubernetes namespaces, integrated out of the box:

| Component | Namespace | What it does |
|---|---|---|
| **CoWeave Workflow** (n8n fork) | `coweave-workflow` | The workflow engine, plus the shared PostgreSQL and Redis the rest of the platform uses |
| **CoWeave AI** | `coweave-ai` | Claude AI service — session router, `claude-cli`, and worker pods |
| **Context Engineering Studio** | `coweave-ce-studio` | The web UI for codifying team context, managing workflow prompts, running your kanban board |
| **Observability** | `coweave-observability` | Grafana, Prometheus, Loki |

`deploy-platform.sh` provisions all of these (plus a small `coweave-infra` namespace for shared infrastructure) in one run. Context Engineering Studio in Enterprise mode isn't a standalone app — it integrates with n8n for SSO and team sync, and shares the PostgreSQL and Redis running in `coweave-workflow`. That's the whole point of Enterprise: one install, one set of credentials, one place to manage everything.

(If you're evaluating CE Studio standalone with no n8n integration, that's Community Edition — different install, different post.)

## Before you start

A checklist you can run through while the VM provisions:

- **VM**: 4+ vCPU, 16 GB RAM, **100 GB root disk plus a separate ≥250 GB data disk** (see Step 0). Single-VM is sized for evaluation, pilots, and small teams.
- **OS**: Ubuntu 22.04+, Debian 12+, RHEL 9+, Rocky Linux 9+, Amazon Linux 2023+, or SUSE 15+. Fresh install recommended.
- **Access**: SSH as a sudo-capable user (e.g. `ubuntu`, `ec2-user`, `azureuser`). You'll create a dedicated `coweave` user in Step 0.
- **Network**: ports 80, 443, and 6443 open inbound. Egress to GitHub, Anthropic, and Docker Hub during install.
- **DNS**: **two** A records pointed at your VM's public IP (see below).
- **Anthropic API key** for the Claude AI service (or per-user Claude Max tokens — see Step 6).
- **The packages**: `coweave-single-vm-{version}.tar.gz` (the platform) and, for workflows, the separate `coweave-workflows-{version}.tar.gz`.

### DNS records — two, not three

The AI service is reached entirely over cluster-internal DNS, so it needs **no public hostname**. Point just these two records at your VM:

```
coweave-workflow.yourcompany.com  →  <your VM IP>   # n8n
ce-studio.yourcompany.com         →  <your VM IP>   # CE Studio
```

`deploy-platform.sh` runs a preflight that resolves each enabled domain and **aborts if it doesn't point at this VM** — this catches the classic "copied a values file from another deploy and left a stale hostname behind" mistake. Kick DNS off first so it's propagated by the time you deploy. Verify from the VM with `nslookup coweave-workflow.yourcompany.com`.

> ⚠️ **CDN / proxy users (Cloudflare, CloudFront, etc.):** set both records to **DNS-only (no proxy)** before deploying. Let's Encrypt HTTP-01 challenges can't reach the certificate solver through a CDN proxy. Once certificates are issued (`kubectl get certificate -A` shows `Ready=True`), you can re-enable the proxy.

> 💡 **Only need an external Claude/MCP caller?** If something *outside* the cluster must reach the AI service (e.g. a custom MCP client on an operator laptop), add a third record `coweave-ai.yourcompany.com` and set `ingress.enabled: true` + `global.domain` in `values-ai.yaml`. Off by default; skip it otherwise.

## Step 0 — Prepare the host (data disk + `coweave` user + Docker)

**~20 minutes.** This runs on a fresh VM *before* you extract the tarball. It's covered in full in the package's `install-readme.md`; the essentials:

### Attach a data disk and put all state on it

Everything CoWeave writes at runtime lives under three paths — `/home/coweave`, `/opt/k3s-storage`, `/opt/coweave-shared-storage`. Keep all three on a **separate persistent data disk** so the VM itself stays stateless and disposable (recreate the VM, reattach the disk, and all data survives).

```bash
# Assuming the data disk shows up as /dev/sdb:
sudo mkfs.ext4 -L coweave-data /dev/sdb
sudo mkdir -p /data
echo 'LABEL=coweave-data  /data  ext4  defaults,nofail  0 2' | sudo tee -a /etc/fstab
sudo mount -a

# Place the three platform paths on the disk via bind mounts
sudo mkdir -p /data/home /data/opt/k3s-storage /data/opt/coweave-shared-storage
sudo mkdir -p /opt/k3s-storage /opt/coweave-shared-storage
{
  echo '/data/home                       /home                       none  bind  0 0'
  echo '/data/opt/k3s-storage            /opt/k3s-storage            none  bind  0 0'
  echo '/data/opt/coweave-shared-storage /opt/coweave-shared-storage none  bind  0 0'
} | sudo tee -a /etc/fstab
sudo mount -a

df -h /home /opt/k3s-storage /opt/coweave-shared-storage   # all three should show the data disk
```

> For a throwaway sandbox you can skip the data disk. For anything with customer data, don't — a detachable disk is portable across regions, instance types, and even clouds in a way VM snapshots are not.

### Create the `coweave` user with UID/GID 60001

All platform workloads run as **UID 60001 / GID 60001**. The values templates hardcode this as `users.coweave.uid`, and every chart's `runAsUser`/`fsGroup` derives from it. Pin it explicitly — if `useradd` picks a default (≥1000), pods fail at deploy time with "can't write to /persistent" permission errors.

```bash
# Ubuntu / Debian:
sudo groupadd -g 60001 coweave 2>/dev/null || true
sudo useradd -m -s /bin/bash -u 60001 -g 60001 coweave
sudo usermod -aG sudo,docker coweave          # RHEL/Rocky/Amazon/SUSE: use 'wheel,docker'

# Copy your SSH key over so you can log in as coweave, then reconnect as coweave:
sudo mkdir -p /home/coweave/.ssh
sudo cp ~/.ssh/authorized_keys /home/coweave/.ssh/
sudo chown -R coweave:coweave /home/coweave/.ssh
sudo chmod 700 /home/coweave/.ssh && sudo chmod 600 /home/coweave/.ssh/authorized_keys
```

Verify: `id coweave` should show `uid=60001(coweave) gid=60001(coweave)`. If `60001` is already taken, either free it or pick custom IDs and align `users.coweave.uid`/`gid` in `values-platform.yaml` later.

### Install Docker

```bash
# Ubuntu / Debian:
sudo apt-get update && sudo apt-get install -y docker.io
sudo systemctl enable --now docker
docker run --rm hello-world   # must succeed as the coweave user (re-login if 'permission denied')
```

> 💡 **Driving the install with Claude Code?** Install the CLI via `npm i -g @anthropic-ai/claude-code`, **not** the standalone Bun-bundled binary — on hardened kernels (Ubuntu 25.10+, GCP `6.17.x-gcp`, `ptrace_scope=1`) the Bun build hits a startup SIGSEGV. `prepare-host.sh` uses the npm install internally.

Everything from here runs as the `coweave` user.

## Step 1 — Unpack the package

**~2 minutes.** The tarball is versioned but extracts to a version-less `coweave-single-vm/` directory by design.

```bash
sha256sum -c coweave-single-vm-*.tar.gz.sha256    # verify integrity
mkdir -p ~/coweave/{releases,config}
mv coweave-single-vm-*.tar.gz ~/coweave/releases/
cd ~/coweave/releases
tar -xzf coweave-single-vm-*.tar.gz               # extracts to ./coweave-single-vm/
ln -sfn coweave-single-vm coweave-single-vm-latest
```

**Why the `latest` symlink?** When the next release ships, you extract it, repoint one symlink, and every command in this guide keeps working unchanged. You never edit a script.

The recommended layout uses two directories: `~/coweave/releases/` (versioned packages) and `~/coweave/config/` (**your** configuration, completely separate from any release). The split is what makes upgrades trivial — your config never moves.

## Step 2 — Configure your values files

**~15 minutes. The only step that needs thought.** Copy all five templates into your config directory, then edit them. The big news: **you don't set any passwords here** — `prepare-host.sh` generates PostgreSQL, Redis, Grafana, and the n8n encryption key into Kubernetes secrets for you.

```bash
cd ~/coweave/releases/coweave-single-vm-latest/config
[ -f ~/coweave/config/values-platform.yaml ]             || cp values-platform-template.yaml      ~/coweave/config/values-platform.yaml
[ -f ~/coweave/config/values-workflow.yaml ]             || cp values-workflow-template.yaml      ~/coweave/config/values-workflow.yaml
[ -f ~/coweave/config/values-ai.yaml ]                   || cp values-ai-template.yaml            ~/coweave/config/values-ai.yaml
[ -f ~/coweave/config/values-ce-studio-enterprise.yaml ] || cp values-ce-studio-template.yaml     ~/coweave/config/values-ce-studio-enterprise.yaml
[ -f ~/coweave/config/values-observability.yaml ]        || cp values-observability-template.yaml ~/coweave/config/values-observability.yaml
```

### `values-platform.yaml` — the cross-chart source of truth (edit first)

Node identity, the admin/ACME email, the `coweave` UID/GID, and SMTP are **platform-wide** settings and live here — not in the per-component files. `prepare-host.sh` requires this file.

```yaml
users:
  coweave:
    uid: 60001                          # must match the host user from Step 0
    gid: 60001

global:
  nodeName: "your-vm-hostname"          # MUST BE SET — must equal the output of `hostname`
  adminEmail: "admin@yourcompany.com"   # MUST BE SET — real address; Let's Encrypt rejects example.com / empty

smtp:
  enabled: false                        # set true once you have SMTP credentials
  host: ""                              # e.g. "smtp-relay.brevo.com", "email-smtp.us-east-1.amazonaws.com"
  port: 587
  user: ""
  sender: "noreply@yourcompany.com"     # the From: domain must be SPF/DKIM-authenticated at your provider
```

> ⚠️ **SMTP sender authentication (required for delivery).** If you enable SMTP, your provider must be authorized to send from `smtp.sender`. Publish the SPF + DKIM records your provider gives you (ideally DMARC) **before** enabling it — otherwise mail is accepted by the relay but **silently dropped**: n8n reports success, nothing appears in any log, and email just never arrives. Per-provider setup is in `docs/operations/SMTP_SETUP.md` inside the package.
>
> **The SMTP password is never in a values file.** Pass it via `export COWEAVE_SMTP_PASSWORD="…"` before running `prepare-host.sh`. To defer email entirely, leave `smtp.enabled: false`.

### `values-workflow.yaml` — the n8n public hostname

```yaml
global:
  domain: "coweave-workflow.yourcompany.com"   # MUST BE SET — must resolve via DNS to this VM
```

Search for `MUST BE REVIEWED` and adjust PostgreSQL / n8n storage sizes if needed (larger for more workflows). Defaults are sized for evaluation.

### `values-ai.yaml` — the Claude API key

```yaml
claude:
  apiKey: "your-anthropic-api-key"   # MUST BE SET (API mode)

# AI ingress is DISABLED by default — in-cluster callers use *.svc.cluster.local,
# so no public domain/DNS record is needed. Only uncomment for an external caller:
# global:
#   domain: "coweave-ai.yourcompany.com"
# ingress:
#   enabled: true
```

> 💡 **Redis password is not set here.** Under the default `secretManagement.strategy: precreated`, `prepare-host.sh` generates it into the `redis-secret` and syncs it into the `coweave-ai` namespace; the AI chart reads it from there.

### `values-ce-studio-enterprise.yaml` — the CE Studio hostname

```yaml
global:
  domain: "ce-studio.yourcompany.com"   # MUST BE SET — must resolve via DNS to this VM
edition: "enterprise"
```

A wrong hostname here breaks password-reset email links, OAuth redirects, and the n8n cookie domain — get it right.

### `values-observability.yaml`

Sensible defaults; the only fields most customers touch are Loki storage sizes (`loki.write.storageSize` / `loki.backend.storageSize`) for longer log retention. Skim and leave defaults for evaluation.

### Wire up the symlinks

The setup and deploy scripts read config from the *release* directory, but your source of truth lives in `~/coweave/config/`. Link them:

```bash
cd ~/coweave/releases/coweave-single-vm-latest/config
ln -sf ~/coweave/config/values-platform.yaml             values-platform.yaml
ln -sf ~/coweave/config/values-workflow.yaml             values-workflow.yaml
ln -sf ~/coweave/config/values-ai.yaml                   values-ai.yaml
ln -sf ~/coweave/config/values-ce-studio-enterprise.yaml values-ce-studio-enterprise.yaml
ln -sf ~/coweave/config/values-observability.yaml        values-observability.yaml
```

On the next release you repeat exactly these commands inside the new release directory — your edits flow through automatically, no copy-pasting.

## Step 3 — Run the infrastructure script

**~10 minutes, mostly hands-off.** Set the SMTP password (only if you enabled SMTP), then run:

```bash
export COWEAVE_SMTP_PASSWORD="your-smtp-password"    # skip if smtp.enabled: false
cd ~/coweave/releases/coweave-single-vm-latest
./scripts/prepare-host.sh --values-folder ~/coweave/config
```

What it does:

- Installs k3s (lightweight Kubernetes), Helm, cert-manager, and the nginx ingress controller
- Creates the storage directories and PersistentVolumes (sized from your values files)
- Creates the platform namespaces
- **Generates the passwords** — PostgreSQL, Redis, Grafana, and the n8n encryption key — and stores them in Kubernetes secrets, syncing Redis into `coweave-ai`
- Issues a Let's Encrypt ClusterIssuer for the ingress

> **Interactive prompts.** On a fresh install the script pauses for the PostgreSQL, Redis, and Grafana passwords — press **Enter to auto-generate** a strong one for each, or `export COWEAVE_POSTGRES_PASSWORD` / `COWEAVE_REDIS_PASSWORD` / `COWEAVE_GRAFANA_PASSWORD` beforehand for an unattended run.

> 🚨 **Back up the n8n encryption key the moment it exists.** It encrypts every credential stored in n8n (GitHub tokens, Slack webhooks, etc.). Lose it and every credential becomes unrecoverable. Grab it right after setup and store it durably (1Password, a vault):
> ```bash
> kubectl get secret n8n-secret -n coweave-workflow \
>   -o jsonpath='{.data.encryption-key}' | base64 -d
> ```

The other generated passwords, any time you need them:

```bash
kubectl get secret postgres-secret -n coweave-workflow -o jsonpath='{.data.postgres-password}' | base64 -d
kubectl get secret redis-secret    -n coweave-workflow -o jsonpath='{.data.redis-password}'    | base64 -d
kubectl get secret grafana-secret  -n coweave-workflow -o jsonpath='{.data.admin-password}'    | base64 -d
```

## Step 4 — Deploy the applications

**~15 minutes, hands-off.**

```bash
cd ~/coweave/releases/coweave-single-vm-latest
./scripts/deploy-platform.sh
```

> ⚠️ **Run from the package root, not from `scripts/`.** The script uses relative paths to find your config symlinks; running it from the wrong directory produces "configuration not found" errors.

It validates all five config files, imports the bundled Docker images into k3s, Helm-installs observability → workflow (n8n + PostgreSQL + Redis) → AI → CE Studio, wires ingress for the two public domains, triggers cert-manager to issue certificates, and waits for every pod to become Ready.

> ✅ **You should see** a success summary ending with your access URLs (`https://ce-studio.yourcompany.com`, `https://coweave-workflow.yourcompany.com`).

## Step 5 — Verify, then bootstrap n8n and CE Studio

**~10 minutes.** First, three checks:

```bash
kubectl get pods -A                 # everything Running across all namespaces
kubectl get certificate -A          # every READY column should be True
./scripts/health-check.sh           # canonical end-to-end check
```

`health-check.sh` is the "is the platform happy?" command — it checks node status, pod health, cross-namespace service discovery (CE Studio → workflow PostgreSQL/Redis), ingress, storage, and DNS, and tells you exactly which subsystem is unhappy if anything's wrong.

Now connect n8n and CE Studio. This is a one-time bootstrap.

**1. Create the n8n owner account.** Open `https://coweave-workflow.yourcompany.com`. On a fresh install the first visit shows an owner-setup form — fill in name, email, and password. This account owns the n8n instance (separate from the CE Studio admin below).

**2. Generate an n8n owner API key.** In n8n: **Settings → n8n API → Create an API key**. Label it `ce-studio-owner-key`, set **No expiration** unless policy demands otherwise, and copy it — **n8n shows it exactly once.**

**3. Complete the CE Studio first-boot wizard.** Open `https://ce-studio.yourcompany.com`. On a fresh install CE Studio presents a **first-boot setup wizard** — there is no pre-seeded admin. Create the first admin account (use a strong password — it's the platform owner, with authority over all teams and integrations).

**4. Paste the n8n key into CE Studio.** Go to **Settings → Integrations → n8n Owner API Key**, paste the key from step 2, and **Save**. CE Studio validates it against n8n before persisting. This instance-level key is what lets CE Studio mint per-team n8n service users and keys downstream.

You're logged in and the two systems are wired together.

## Step 6 — Set your personal Claude token

**~3 minutes.** Beyond the API key in `values-ai.yaml`, every user who triggers workflows sets their **own** Claude token, so Claude Max usage is attributed to them personally rather than a shared key.

On your **laptop** (not the server):

```bash
npm install -g @anthropic-ai/claude-code
claude setup-token          # opens your browser — log in with your Claude Max account
```

Copy the printed token (starts with `sk-ant-oat01-…`), then in CE Studio go to **Settings → AI Service Auth**, paste it, and **Save Token**. The banner should change to "Token configured."

> An Anthropic API key (`sk-ant-api03-…`, pay-per-token, no Max subscription) also works in the same field — cost accounting differs. CE Studio warns 30 days before a token expires; re-run `claude setup-token` and paste the new value.

## When something goes wrong

The issues we actually see in the field, in rough order of frequency:

### 1. DNS isn't resolving / deploy preflight aborts

`deploy-platform.sh` refuses to proceed if `global.domain` doesn't resolve to this VM. Check `nslookup coweave-workflow.yourcompany.com` and `nslookup ce-studio.yourcompany.com`. If it resolves from the VM but not your laptop, propagation just hasn't reached you — wait and retry. To defer DNS for a staging cutover only: `export COWEAVE_SKIP_DOMAIN_CHECK=1` before deploying (testing).

### 2. Ingress returns 502 / certificate stuck

Cert-manager hasn't issued the SSL certificate yet. Watch `kubectl get certificate -A` — each domain's `READY` should flip to `True` within a minute or two. If it stays `False`, `kubectl describe certificate <name> -n <ns>` shows the ACME error — almost always a DNS record that hasn't propagated, or a CDN proxy intercepting the HTTP-01 challenge (set DNS to DNS-only).

### 3. Claude AI pods crashing with Redis auth errors

Under the default `precreated` secret strategy the Redis password lives only in the `redis-secret`, generated by `prepare-host.sh` and synced into `coweave-ai`. A crash here means the secret is missing or out of sync, not that two values files disagree:

```bash
kubectl get secret redis-secret -n coweave-workflow
kubectl get secret redis-secret -n coweave-ai        # keys must match
# If missing in coweave-ai, re-run setup then redeploy just the AI component:
./scripts/prepare-host.sh
./scripts/deploy-platform.sh coweave-ai
```

### 4. Permission errors on persistent volumes at deploy time

The `coweave` host user wasn't created with UID/GID **60001**, so pods running as 60001 can't write to the shared mount. Recreate the user with the pinned IDs (Step 0), or align `users.coweave.uid`/`gid` in `values-platform.yaml` to whatever the host actually uses, then re-run `prepare-host.sh` and `deploy-platform.sh`.

### 5. Configuration changes aren't taking effect

Almost always means you edited a file inside the release directory instead of the source-of-truth in `~/coweave/config/`. The release files are symlinks — always edit `~/coweave/config/values-*.yaml`.

### 6. Email silently never arrives

SMTP is authenticated by the relay but the sending domain isn't SPF/DKIM-authorized, so mail is accepted and dropped with no error. Publish the SPF + DKIM records from your provider for the `smtp.sender` domain. See `docs/operations/SMTP_SETUP.md` in the package.

For anything else, `./scripts/health-check.sh` will tell you exactly which subsystem is unhappy. Start there.

## Sidebar — Upgrading later

When the next release lands, the upgrade is four steps — your config in `~/coweave/config/` is never touched:

```bash
# 1. Extract the new release alongside the existing one
cd ~/coweave/releases
tar -xzf coweave-single-vm-NEW-VERSION.tar.gz

# 2. Repoint the latest symlink
ln -sfn coweave-single-vm coweave-single-vm-latest    # (version-less extract dir)

# 3. Re-create the config symlinks inside the new release
cd coweave-single-vm-latest/config
for f in values-platform values-workflow values-ai values-ce-studio-enterprise values-observability; do
  ln -sf ~/coweave/config/$f.yaml $f.yaml
done

# 4. Redeploy — your config is reused automatically
cd ~/coweave/releases/coweave-single-vm-latest
./scripts/deploy-platform.sh
```

## Sidebar — Getting onto a GCP VM (or any cloud VM)

If this is your first time SSHing into the instance, here's the end-to-end flow — same shape on AWS or Azure, just different console screens.

**1. Generate an SSH key on your laptop** (if you don't have one): `ssh-keygen -t ed25519 -C "you@yourcompany.com"`. This gives `~/.ssh/id_ed25519` (private) and `.pub` (public).

**2. Add the public key to the VM.** In the Google Cloud Console: **Compute Engine → VM instances → your VM → Edit → SSH Keys → Add item**, paste the contents of `~/.ssh/id_ed25519.pub`, Save. GCP uses the username at the end of the key as your Linux login.

**3. Add the VM to your local `~/.ssh/config`** so `ssh coweave-vm` works — and so VS Code Remote-SSH can find it:

```
Host coweave-vm
  HostName <your-vm-public-ip>
  User <your-initial-login>     # your sudo user; switch to `coweave` after Step 0
  IdentityFile ~/.ssh/id_ed25519
  IdentitiesOnly yes
```

**4. Connect from VS Code.** Install **Remote - SSH**, open the Command Palette, run **Remote-SSH: Connect Current Window to Host…**, pick `coweave-vm`. The VS Code terminal is now a shell *on the VM*, and every step of this guide happens inside it.

**5. Move the tarballs onto the VM.** Either drag them into the VS Code file tree (SFTP), or `scp coweave-single-vm-*.tar.gz coweave-vm:~/`. After Step 0 you'll typically place them under `~/coweave/releases/` owned by `coweave`.

> 💡 **Run the long scripts in `tmux`** so a sleeping laptop doesn't kill the deploy mid-run:
> ```bash
> tmux new -s coweave
> ./scripts/prepare-host.sh --values-folder ~/coweave/config
> # Ctrl-b d to detach; `tmux attach -t coweave` to come back
> ```
